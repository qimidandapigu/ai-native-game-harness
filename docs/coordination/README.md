# 并行开发协调说明

本目录是多任务协作的单一入口，解决“多个线程共用一个仓库、彼此不知道谁在改什么”的问题。

## 文件职责

- `STATUS.md`：当前仓库快照和集成风险。只由合并管理任务维护。
- `claims/<task-id>.md`：每个任务自己的文件认领和交接记录。任务只写自己的文件。
- 根目录 `AGENTS.md`：所有 Codex 任务必须遵守的稳定规则。

产品定位和技术事实仍以对应源码、协议文档和架构文档为准；`STATUS.md` 只记录某一时刻观察到的工作状态，不替代产品文档。

## 推荐工作流

### 1. 新任务开始

1. 阅读根目录 `AGENTS.md` 和本目录 `STATUS.md`。
2. 执行 `git status --short --branch` 和 `git worktree list`。
3. 创建独立分支和 worktree，例如：

   ```powershell
   git worktree add ..\ai-native-game-harness-worktrees\<task-name> -b task/<task-name> origin/main
   ```

4. 在 `claims/` 新建以 Codex task id 命名的认领文件，填写目标、允许修改的路径、共享热点和验证计划。

### 2. 开发中

- 只写认领路径。
- 若必须触碰共享热点，先通知合并管理任务；不要通过“最后保存覆盖”解决冲突。
- 安装包构建、本机安装、Steam Mod 复制和 DSH profile 更新属于全局独占操作，执行前必须确认没有另一个任务正在做。
- 生成物可以用于验收，但不能替代源代码交接。

### 3. 交接

在自己的 claim 文件中写清：

- 实际改动文件；
- 关键设计决定；
- 自动测试结果；
- 尚未完成的真实环境验证；
- 生成物位置和正在运行的进程；
- 建议由合并管理任务如何集成。

不要自行修改 `STATUS.md`，也不要在没有授权时提交或推送。

## Claim 模板

```markdown
# <任务标题>

- Task ID: `<id>`
- 状态：计划中 / 开发中 / 待集成 / 完成
- 分支与 worktree：`<branch>` / `<absolute path>`
- 目标：<一句话>
- 允许修改：
  - `<path/**>`
- 共享热点：无 / `<path>`（已获得协调）
- 不修改：<明确排除项>
- 验证：<命令和结果>
- 交接：<未完成事项、生成物和进程>
```

## 合并顺序

合并管理任务按以下顺序处理：

1. 冻结新的共享目录写入并收集所有 claim。
2. 保存 `git status`、`git diff --stat` 和版本号快照。
3. 先整合协议与核心 Runtime，再整合单个游戏，最后整合 Desktop、安装脚本、锁文件和公共文档。
4. 解决 `origin/main` 差异后再统一生成锁文件和安装包。
5. 分层测试：包级测试 → 平台测试 → 安装器 → 真实游戏。
6. 用户确认后才提交或推送。
